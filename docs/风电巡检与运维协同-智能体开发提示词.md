# 风电巡检与运维协同智能体开发提示词（MVP 优化版）

你是一名资深 AI 应用工程师，帮我开发一套“风电巡检与运维协同智能体系统”。请严格按我给出的技术栈和约束执行，不要自行替换框架、不要引入我没要求的中间件。

## 【项目背景】

本项目来自青原新能源的原创合成课程案例。合成访谈基线为日均告警 280 条、误报率 38%，60 台风机每天约 120 次点检，巡检员每天重复归并告警约 3 小时；现有流程是“告警 → 趋势核查 → 现场检查 → 工单派发 → 检修 → 值班确认”，但各节点等待和处理时间尚未分别计量。

首期目标是在 5 台风机上进行 8 周受控试点，先历史回放，再与现流程并行。重大告警漏报必须为 0；误报率 15% 和有效告警响应 20 分钟是待验证目标，判定来源、起算点和统计分母必须可配置、可审计，不能把合成数字写成真实验收结果。

## 【MVP 范围】

本 MVP 必须包含以下四组能力和一项开源协作成果：

1. FastAPI 后端与可运行的最小业务闭环。
2. 项目内轻量 Agent Harness，负责显式状态机、受限工具调用、人工关卡和评估记录。
3. RAG 知识库、LLM Wiki 和知识图谱，所有内容保留来源、版本和组织边界。
4. SaaS 管理员与分层用户权限，至少隔离平台、组织、角色和风场数据范围。
5. 在我确认目标外部仓库后，围绕同一个真实问题提交 1 个高质量 Issue 和 1 个关联 PR。

不做真实设备控制、自动安全审批、正式工单自动写入、无限自主循环、跨租户检索、自动外发或自动合并 PR。

## 【系统定位】

系统是一套只读、可追溯、带人工复核的业务核对助手，提供：

1. 授权资料读取与数据质量校验。
2. 确定性告警去重，以及带原记录引用的模型聚类建议。
3. 检修资料和交接草稿生成。
4. Harness 显式状态机、工具白名单、超时与幂等控制。
5. RAG 检索、带来源的 LLM Wiki 页面和可追溯知识图谱。
6. SaaS 分层权限、人工确认、退回、接手、签核和完整审计。
7. 技术评估、业务指标、反馈闭环与运营报表。

系统不是设备控制系统，不是自动安全审批系统，也不是无人值守工单执行系统。没有模型时必须能退化为确定性规则与人工模板流程。

## 【用户与权限】

- 平台管理员：管理组织、系统开关和平台配置；默认不能查看组织业务正文，敏感操作单独审计。
- 组织管理员：管理本组织用户、角色、知识库和授权范围；不自动获得业务或安全审批权。
- 运维总监：管理本组织试点范围、预算和继续或停止决定。
- 风场巡检员：查看授权告警与趋势、复核或退回建议、编辑个人草稿。
- 检修计划员：校核资料、维护交接草稿、发起复核和升级异常。
- SCADA 工程师：维护只读接口、数据契约、质量队列和快照恢复。
- 作业安全经理：审查权限、安全、留存、审计和人工兜底，拥有风险否决权。
- 电站值班长：核对服务结果、完成口径、争议与反馈。

每次请求必须同时校验 `org_id`、角色动作权限和风场或资料数据范围。所有业务表包含 `org_id`，所有查询在服务端强制过滤；直接猜测记录 ID、Wiki ID、图节点 ID 或运行 ID 也不能越权。最终决定、资产变更、对外承诺、高空作业、停送电和天气禁限必须由对应授权人员处理，禁止借号或通过提示词绕过。

## 【技术栈，不许替换】

- 后端：Python 3.12、FastAPI、Pydantic v2、SQLAlchemy 2.0。
- 数据库：SQLite，使用 SQLAlchemy ORM；训练阶段不得换成其他数据库或新增消息队列。
- 前端：React 18、TypeScript、Vite，不引入额外 UI 框架。
- Agent Harness：在项目内用 Python 显式状态机实现，不引入 Harness.io、LangChain、LlamaIndex 或其他智能体框架。
- RAG：文档分块、Embedding、NumPy 余弦相似度和 SQLite 向量存储，不引入独立向量数据库。
- LLM Wiki：由授权资料生成带来源、版本和修订记录的 Wiki 页面。
- 知识图谱：使用 SQLite 关系表保存节点、边和来源证据，不引入 Neo4j。
- 模型与 Embedding 接入：通过标准 HTTP 调用 OpenAI 兼容接口；提供商、模型名、地址和密钥全部从 `config.yaml` 与环境变量读取。
- 测试：pytest、pytest-asyncio、httpx；前端使用 Vitest。
- 代码检查：Ruff。
- 不引入 Celery、Redis、Kafka、RabbitMQ、Elasticsearch、Kubernetes 或其他未要求的框架和中间件。
- 如需新增依赖，先停止并说明理由，等我确认后再修改。

## 【Harness 硬约束】

1. 状态限定为 `received → scope_checked → permission_checked → evidence_checked → retrieved → draft_generated → review → approved/rejected/needs-info`，任意阶段可进入 `blocked/degraded/manual`。
2. 状态只能按白名单迁移，模型不得直接修改状态、审批结果或权限。
3. 工具仅允许只读授权资料、当前范围知识检索、读取原分块、创建复核草稿和请求人工复核。
4. 不提供设备控制、正式工单写入、自动外发、自动合并或用户提权工具。
5. 每次运行保存 `run_id`、`org_id`、`business_id`、输入哈希、状态、规则/模型版本、检索引用、输出、人工动作和时间戳。
6. 工具超时、空结果和来源异常必须显式失败；重试次数从配置读取且有上限，禁止无限自主循环。
7. 人工关卡不得由模型、管理员或前端参数跳过。

## 【知识库硬约束】

1. RAG 先按组织、数据范围、版本和有效期过滤，再做相似度检索。
2. 检索结果必须返回 `chunk_id`、原文摘录、来源、版本和得分，回答保留相同引用。
3. 无有效资料、低于阈值或来源失效时返回资料不足，不得根据常识补写业务事实。
4. 版本冲突时同时展示两个版本并转人工，不自动选择较新或较宽松条款。
5. LLM Wiki 每段保留来源和生成版本；人工修订形成新版本，不覆盖原文和历史页面。
6. 知识图谱节点至少覆盖风机、告警、业务事件、资料、规则、角色和交接任务；关系必须能回溯来源。
7. 模型只能生成图关系候选，影响安全、权限和验收的关系必须人工确认后生效；图谱不得直接触发业务动作。
8. 跨组织召回、跨组织 Wiki 或图节点读取必须为零，并写入自动化测试。

## 【数据红线，硬约束】

1. 只读取明确授权的合成或脱敏资料；禁止自动启停风机、修改保护阈值或写入 SCADA。
2. 首期不写入 EAM 正式工单，只生成待人工确认草稿。
3. 无原始来源、来源失效或事实引用不足时，不生成确定结论，返回 `needs-info` 或 `manual`。
4. 主编号、事件时间或版本有歧义时进入人工修复队列，不进入自动推荐样本。
5. 超过一个更新周期的数据必须标记“待刷新”；接口中断只能展示带时间戳的只读快照并提示“暂未更新”。
6. 重连和重试必须按业务编号、输入版本和操作类型保证幂等，不得重复生成待办。
7. 重大告警漏报、跨租户访问、越权、自动设备控制、来源断链或人工兜底失效必须触发停止和审计。
8. 日志不得记录账号口令、访问令牌或无关个人信息；配置和示例文件不得包含真实密钥。
9. 训练评价记录的 90 天留存只作为可配置演练默认值，真实期限必须由组织制度确认。
10. 所有合成样本、模型输出、测试结果和 ROI 必须显著标注性质，不得伪装成真实客户数据或验收结论。

## 【统一业务与接口要求】

- 正常建议状态为 `review`，材料缺失为 `needs-info`，版本冲突为 `manual`，无权限或越界为 `blocked`，来源中断为 `degraded`。
- 每条建议必须返回业务编号、原记录引用、资料版本、规则版本、模型版本、待确认字段和审计追踪。
- 人工修改不得覆盖原始记录，必须形成新版本并保留修改人、修改时间和原因。
- 只有下一岗位具名人员确认接手后，上一岗位待办才可关闭；发送消息不等于完成交接。
- 业务指标使用唯一业务编号、固定分母、固定统计周期和明确排除规则；同一业务不得重复计算成功。
- 所有配置集中于 `config.yaml`，敏感值只通过环境变量引用，禁止把密钥、模型地址写死在代码里。
- 所有对外接口返回统一结构：`{"ok": bool, "data": ..., "error": {"code": str, "msg": str}}`。
- 失败时 `ok=false`、`data=null`，错误码至少包括 `VALIDATION_ERROR`、`TENANT_MISMATCH`、`PERMISSION_DENIED`、`SOURCE_MISSING`、`VERSION_CONFLICT`、`SOURCE_STALE`、`SOURCE_UNAVAILABLE`、`DUPLICATE_REQUEST`、`HUMAN_REVIEW_REQUIRED` 和 `INTERNAL_ERROR`。
- 业务状态与 HTTP 状态码分别定义，不以 HTTP 200 暗示业务成功。

最小页面包括登录、业务工作台、知识库检索、Wiki/图谱、Harness 运行详情、人工复核和组织管理。前端只负责展示和提交，后端必须重新执行权限、状态迁移与引用校验。

至少实现：

- `POST /api/v1/documents`

- `POST /api/v1/reviews/{id}/reject`

## 【代码规范】

- 每个函数写中文 docstring，说明入参、出参、失败时的行为。
- 关键业务逻辑（安全审查、租户隔离、权限校验、人工确认）必须写中文行内注释，说明为什么这么卡。
- 配置文件统一放 `config.yaml`，禁止把密钥、模型地址写死在代码里。
- 每行代码必须添加中文注释，包括配置示例和测试代码；不为了凑注释改变原有语义。
- 对失败显式返回稳定错误码，不吞异常，不把异常堆栈或敏感配置返回给客户端。
- 规则判断与模型判断分层，模型不得直接获得写入工具或绕过人工关卡。
- 测试必须包含正常、边界、对抗、跨租户、权限、故障、重复请求和恢复路径。

## 【测试与验收】

至少覆盖正常业务、材料缺失、版本冲突、身份无权限、跨租户访问、来源不可用、越界动作、提示词注入、未知样本、跨模块请求和重复请求。

必须额外验证：

1. Harness 非法状态迁移被拒绝，人工关卡无法跳过。
2. RAG 无来源拒答、版本冲突转人工、跨组织零召回。
3. Wiki 每段有来源且修订有版本，图关系候选需人工确认。
4. 直接访问其他组织文档、Wiki、图节点、运行或审计 ID 均被拒绝。
5. 所有业务用例断言业务写入次数和外发次数均为 0。
6. 固定输入、规则、模型、依赖和资产哈希，保存 expected/actual、引用与审计轨迹。

技术用例不得写成真实业务验收；真实 5 台 8 周指标仍需脱敏样本、人工标注和组织签核。
